# Xasha API contract

Status: Secret endpoints, operational safeguards, browser-origin policy, and maintenance mode implemented. Envelope version 1 is independent of route naming; routes have no version prefix. The future frontend origin remains undecided.

For integration examples and self-hosting, see [the developer guide](developers.md). Machine-readable endpoint schemas are in [OpenAPI](openapi.json).

This document translates the backend requirements in `PRD.md` into an API agreement. The protocol choices below are implemented. The 32 KiB text limit, 24-hour default expiry, and expiry choices of 1 hour, 24 hours, and 7 days are agreed.

## Conventions

- Secret endpoints use `/secrets` without a version prefix and require HTTPS.
- Request and response bodies use JSON. Body-bearing requests require `Content-Type: application/json`; other content types receive `415`.
- All API responses, including errors, carry `Cache-Control: no-store`.
- Times in responses are UTC ISO 8601 strings. Expiry is evaluated using server time.
- Reject unknown request fields, including plaintext and key fields. Never echo submitted values in errors.
- There are no accounts, cookies, or login requirements.
- `GET`, `HEAD`, and `OPTIONS` never retrieve content or delete records. Unsupported methods on known secret routes return `405`; preflight requests remain side-effect free.

## Endpoint overview

| Action | Endpoint | Success |
| --- | --- | --- |
| Create | `POST /secrets` | `201` with reference, deletion token, and expiry |
| Consume | `POST /secrets/{id}/consume` | `200` with the encrypted envelope |
| Delete | `POST /secrets/{id}/delete` | `204` with no body |
| Liveness | `GET /health` | `200` with service status; already implemented |
| Readiness | `GET /ready` | `200` when active and D1 metadata is readable, otherwise `503` |

There is no endpoint to list secrets, inspect their availability, recover deletion tokens, or retrieve content without consuming it. The backend does not serve share or delete confirmation pages.

Readiness returns `{ "status": "ready", "service": "xasha" }` or `{ "status": "unavailable", "service": "xasha" }`. It uses a status response rather than the secret API's error envelope and exposes no secret content or counters. See [monitoring](monitoring.md) for the exact check and its limitations.

## Encrypted envelope

Envelope version 1 uses AES-256-GCM, a 12-byte IV, and a 16-byte authentication tag appended to the ciphertext. Binary fields use canonical, unpadded base64url. The version fixes the encryption parameters, so there is no caller-controlled algorithm field.

```json
{
  "version": 1,
  "iv": "<base64url encoded 12-byte IV>",
  "ciphertext": "<base64url encoded ciphertext with appended tag>"
}
```

Client integration expectations: encrypt UTF-8 text using a new random 32-byte key and random IV for each secret, with no additional authenticated data in version 1. Neither the key nor plaintext is part of any API request. The backend checks structure and size but cannot prove that content was encrypted correctly or that it represents text.

Encrypted request limits for the agreed 32 KiB UTF-8 plaintext allowance:

- Plaintext allowance: 32,768 bytes, enforced by the client only.
- Decoded ciphertext including tag: 17–32,784 bytes. The minimum corresponds to a nonempty plaintext plus the tag.
- IV: exactly 12 decoded bytes.
- Entire uncompressed JSON request: at most 48 KiB (49,152 bytes), including metadata and whitespace. Enforce the limit while reading; do not rely solely on `Content-Length`.
- Compressed request bodies are unsupported in version 1.

These limits apply to bytes, not character counts. Encrypting malformed data can still consume a secret even if a recipient cannot decrypt it.

## Create a secret

`POST /secrets`

```json
{
  "envelope": {
    "version": 1,
    "iv": "<base64url IV>",
    "ciphertext": "<base64url ciphertext and tag>"
  },
  "expiresIn": 86400
}
```

`envelope` is required. `expiresIn` is an integer duration in seconds. Accepted values are `3600`, `86400`, and `604800`; the omitted-value default is `86400`. Null, arbitrary durations, unsupported versions, and malformed encodings are rejected before storage.

Success: `201 Created`.

```json
{
  "id": "<random secret reference>",
  "deleteToken": "<independent random deletion token>",
  "expiresAt": "2026-10-07T12:00:00.000Z"
}
```

Credentials: the reference contains 24 random bytes encoded as base64url (32 characters); the deletion token contains 32 independent random bytes (43 characters). They are generated by the backend. The backend stores only a hash of the deletion token and returns the token once, after successful storage.

The client constructs the share link using `id` and puts the encryption key in its URL fragment. It constructs the private delete link separately, preferably with the deletion token in a fragment so merely opening that link does not send the token to the server. These client links are not API endpoints.

Creation is not idempotent in version 1. Retrying after an uncertain response can create a second secret. An orphaned secret expires normally; the backend cannot recover its deletion token.

## Consume a secret

`POST /secrets/{id}/consume`, with no request body and no deletion token.

Success: `200 OK`.

```json
{
  "envelope": {
    "version": 1,
    "iv": "<original base64url IV>",
    "ciphertext": "<original base64url ciphertext and tag>"
  }
}
```

The encrypted envelope is returned unchanged. Retrieval and consumption form one atomic operation; no later acknowledgement is required. Expiry is checked within that operation. At most one concurrent request receives the content.

Used, expired, deleted, missing, and malformed secret references all produce `404` with the same response:

```json
{
  "error": {
    "code": "SECRET_UNAVAILABLE",
    "message": "This secret is no longer available."
  }
}
```

No automatic retry or response replay is permitted for consumption. A lost response or failed client decryption does not restore the secret. A service error does not establish whether consumption happened; clients must not interpret it as a safe guarantee to retry.

## Delete a secret

`POST /secrets/{id}/delete`

```json
{
  "deleteToken": "<deletion token returned at creation>"
}
```

Send the deletion token in the JSON body, never a query string or API path. The token must match the stored hash. It authorizes deletion only.

Success behavior: return `204 No Content` only when this request actually deletes an available, unexpired secret. Deletion and consumption compete atomically for the same secret. If consumption wins, deletion cannot recall released content.

Missing, expired, consumed, or deleted secrets, malformed references, and incorrect well-formed tokens produce a uniform `404` with code `DELETE_UNAVAILABLE` and message `This secret could not be deleted. It may already be unavailable, or the delete link may be invalid.` No cause is disclosed. A missing or structurally malformed body/token receives `400`.

Deletion retries never return content. A retry after a successful deletion whose response was lost may receive `404`, so clients must not interpret that response as proof that the earlier deletion failed.

## Other errors

All errors use `{ "error": { "code": "...", "message": "..." } }` with fixed messages that do not include submitted data.

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | `INVALID_REQUEST` | Invalid JSON, fields, envelope, expiry, or deletion request |
| `403` | `ORIGIN_NOT_ALLOWED` | Browser origin is outside the exact allowlist and is not same-origin |
| `403` | `PREFLIGHT_NOT_ALLOWED` | Browser preflight asks for unsupported methods or headers |
| `405` | `METHOD_NOT_ALLOWED` | Unsupported method on a known route; include `Allow` |
| `413` | `PAYLOAD_TOO_LARGE` | Request or decoded payload exceeds limits |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Unsupported request content type or encoding |
| `429` | `RATE_LIMITED` | Usage limit reached; include `Retry-After` when known |
| `503` | `SERVICE_UNAVAILABLE` | Temporary dependency failure or creation capacity exhausted |
| `500` | `INTERNAL_ERROR` | Unexpected server failure, without internal details |

Malformed requests are validated before any mutation. Successful reads from a prior cache must never substitute for consumption. Do not expose ciphertext, tokens, request bodies, or secret reference paths in application logs and analytics; deployment logging needs equivalent review.

## Remaining operational decisions

- Add the future frontend's exact origin when known; the current policy allows same-origin browser requests and non-browser clients. CORS is not authorization.
- Review initial operational defaults: 10 creation attempts per IP per minute per Cloudflare location, 10,000 stored records, and a 50 MiB stored payload budget. See README for accounting and limiter caveats.
- Follow `docs/recovery.md`: pause operations and recover into a fresh empty database rather than serving historical secret rows. Manual Cloudflare restores are not automatically detected.
